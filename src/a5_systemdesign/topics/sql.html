SQL Databases: Systems Engineering Handbook

A rigorous exploration of relational database internals, transaction processing, concurrency control, and production scaling implications.

Executive Summary

A relational database management system (RDBMS) is fundamentally a highly structured data storage abstraction overlaid with a concurrent state machine. At its core, an RDBMS guarantees logical data consistency (ACID) against hardware failures, concurrent mutations, and complex querying patterns, masking the brutal reality of disk I/O latency and system crashes from the application layer.

System Design Context

When selecting a datastore, an RDBMS is typically the default choice for strongly structured, highly relational data requiring strict consistency. The primary tradeoffs involved are write-throughput limits imposed by strict disk flushing (Write-Ahead Logging) and horizontal scaling friction due to distributed consensus overhead in ACID transactions.

Mental Models

The Ledger: Write-Ahead Logging (WAL)

Think of the database not as a collection of tables, but as a sequential, append-only log of changes (the WAL). The tables you query are simply materialized views of this log.

  • The Insight: Random I/O is slow; sequential I/O is fast. By appending to a log sequentially, the database confirms a transaction quickly, deferring the expensive, random I/O required to update actual table pages on disk.
  • Crash Recovery: If the power goes out, the database replays the ledger from the last known checkpoint to reconstruct the state (ARIES protocol).

The Tree: B+ Trees

Imagine a massive, sorted physical card catalog. Instead of searching a million records linearly $O(N)$, you jump through a hierarchy of index cards, reducing the search space exponentially $O(\log N)$.

  • The Insight: Disk blocks are large (e.g., 8KB). A B+ Tree is designed specifically to optimize disk reads by maximizing the fan-out ratio, ensuring the tree remains shallow (typically 3-4 levels deep even for billions of rows).

The Time Machine: MVCC

Instead of locking a row exclusively and blocking readers during a write, the database creates a completely new version of the row with a newer timestamp/transaction ID.

  • The Insight: "Readers do not block writers, and writers do not block readers." Queries operate on a snapshot of the database at the time they began, ignoring newer, uncommitted row versions.

Core Architecture

A production-grade RDBMS operates as a multi-layered pipeline, translating high-level declarative SQL into low-level block I/O operations.

1. Transport & Connection Manager +

Handles TCP/IP connections, authentication, and session state. A critical production consideration is that processes/threads here are heavy. Operating systems struggle with context-switching thousands of connections, which is why connection pooling (e.g., PgBouncer) is mandatory at scale.

2. Query Parser & Optimizer +

The parser converts SQL into an Abstract Syntax Tree (AST). The cost-based optimizer (CBO) then evaluates multiple execution paths (e.g., Sequential Scan vs. Index Scan, Hash Join vs. Nested Loop) using statistical metadata about the tables (cardinality, histograms) to generate the cheapest execution plan.

3. Buffer Pool Manager +

The database relies on its own memory manager rather than the OS page cache. It pre-fetches pages from disk into memory, manages dirty pages, and evicts pages using algorithms like Clock Sweep or LRU. This guarantees predictability over I/O patterns.

Storage Engine & Indexing

Page Layout (Slotted Pages)

Disks are read in blocks (Pages), typically 8KB. Within a page, rows (tuples) are not appended sequentially from top to bottom. Instead, an RDBMS uses a Slotted Page architecture:

  • Header: Metadata, LSN (Log Sequence Number).
  • Slot Array: Array of pointers at the beginning of the page growing downward.
  • Tuples: Actual row data appended from the end of the page growing upward.

This decoupling allows variable-length rows to be updated or compacted without changing the row's logical physical ID (used by indexes).

B+ Trees: The Heart of the Database

Standard indexes are implemented as B+ Trees. Unlike binary trees, B+ Trees are wide and shallow. Only the leaf nodes contain actual data or pointers to data; internal nodes purely route queries.

Clustered vs. Secondary Indexes

In a Clustered Index (e.g., InnoDB Primary Key), the leaf nodes are the data rows. There can only be one per table. In a Secondary Index, the leaf nodes contain the index key and a pointer to the clustered index (or physical heap location). Therefore, traversing a secondary index often requires an expensive secondary lookup (Index-Only Scans avoid this).

Concurrency: ACID & MVCC Deep Dive

Maintaining ACID properties concurrently is the most complex engineering feat in an RDBMS.

Multi-Version Concurrency Control (MVCC)

To implement the Isolation property without crushing performance via locking, modern systems (PostgreSQL, InnoDB) use MVCC.

-- Example tuple internal representation
{
  xmin: 1050,  /* Transaction ID that inserted this row */
  xmax: 1082,  /* Transaction ID that deleted/updated this row */
  data: "user_data..."
}

When a transaction begins, it receives a snapshot ID. It will only read rows where xmin is committed and earlier than the snapshot, and where xmax is either null or later than the snapshot. An UPDATE is physically implemented as an INSERT of a new row and a DELETE of the old row.

Scaling & Distributed Systems Implications

RDBMS scale up vertically with ease, but horizontal scaling introduces CAP theorem realities.

Replication vs. Partitioning (Sharding)

Replication scales reads by maintaining copies (Leader-Follower). The tradeoff is replication lag (stale reads). Partitioning scales writes by splitting data across nodes based on a partition key (e.g., Consistent Hashing). The tradeoff is the loss of distributed ACID guarantees (joins across shards become RPC calls).

Two-Phase Commit (2PC)

When executing a transaction across multiple database nodes, atomicity must be preserved. A coordinator node asks all participants to prepare to commit (Phase 1). Only if all vote "yes", the coordinator commands a commit (Phase 2). This is a blocking protocol; if the coordinator crashes during Phase 2, locks are held indefinitely, causing severe production outages.

Production Engineering Perspective

In production environments, theoretical optimizations yield to operational survivability.

Critical Telemetry

  • Buffer Cache Hit Ratio: Should be > 99%. If it drops, the database is thrashing disk I/O.
  • Replication Lag: Measured in bytes or seconds. High lag means read replicas serve stale data, risking business logic errors.
  • Long-running Transactions: Holds back the MVCC horizon, preventing garbage collection.

Lock Contention

Avoid hot rows. If 1000 concurrent requests try to decrement inventory on a single `product_id`, they serialize on row-level locks. This spikes connection queues. Architecturally, shift this to batched writes, event sourcing, or eventual consistency patterns if throughput demands it.

Garbage Collection (Vacuum)

Because MVCC creates multiple versions of rows, "dead tuples" accumulate. Processes like Postgres Autovacuum reclaim this space. A critical production failure mode is "Transaction ID Wraparound", where an un-vacuumed database runs out of 32-bit transaction IDs, forcing an emergency shutdown to prevent data corruption.

Interview Deep Dive

High-signal technical architecture questions.

Architecture

Why does a database use its own Buffer Pool instead of relying entirely on the OS Page Cache?

Click to reveal architecture reasoning

The OS cache uses generic heuristics (like LRU) that don't map to database workloads. An RDBMS knows its query plans; it knows if a sequential scan will pollute the cache and can employ strategies like "ring buffers" to avoid evicting frequently accessed index pages. Furthermore, the DB needs strict control over write-ordering (WAL protocol) to guarantee durability, which OS caches obscure.

Concurrency

Explain "Write Skew" and why Repeatable Read isolation does not prevent it.

Click to reveal the edge case

Write Skew occurs when two transactions read overlapping datasets, make a decision, and write to different rows. Example: A shift requires min 1 doctor on call. Alice and Bob both read 2 doctors. Alice withdraws, Bob withdraws. Both commit. Now 0 doctors are on call. Repeatable Read prevents dirty reads/non-repeatable reads on specific rows, but doesn't track read-write dependencies across predicates. Serializable isolation is required.

Production

What happens to the database when you add an index to a 50GB table in production?

Click to reveal operational realities

A standard CREATE INDEX takes a Share lock, blocking all writes (INSERT/UPDATE/DELETE) to that table until the index is built, causing severe downtime. In production, you must use CREATE INDEX CONCURRENTLY (Postgres) or ALGORITHM=INPLACE, LOCK=NONE (MySQL), which builds the index in multiple passes without blocking writes, though it takes longer and consumes more CPU.

Common Misconceptions

"Indexes always make queries faster." +

Reality: Indexes speed up lookups but slow down mutations (INSERT, UPDATE, DELETE) because every index must be synchronously updated. Furthermore, if the query planner detects an index returns a large percentage of the table (low selectivity), it will perform a Sequential Scan anyway, rendering the index pure overhead.

"Transactions guarantee atomicity instantly." +

Reality: Atomicity during runtime hides intermediate state, but physical storage is continuous. A rollback isn't an "undo" in memory; it involves writing a compensation/abort record to the WAL and letting the vacuum/undo-log process clean up the physically written, but logically uncommitted, tuples later.

"Primary keys naturally prevent fragmentation." +

Reality: If using a UUID v4 as a primary key in a clustered index (InnoDB), you cause massive fragmentation. UUIDs are random, meaning new rows are inserted randomly across the B+ Tree, causing page splits and heavy random disk I/O. Use sequential IDs (ULID, Snowflake) for clustered indexes.
