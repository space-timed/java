Load Balancers

The central nervous system of distributed architectures. Far beyond simple traffic distributors, modern load balancers act as API gateways, TLS terminators, health monitors, and backpressure mechanisms. Understanding their internal mechanics is critical for building fault-tolerant, low-latency infrastructure at scale.

First Principles & Mental Models

At its core, a load balancer solves the capacity problem and the reliability problem. A single compute instance has finite resources (CPU, Memory, File Descriptors, Network Bandwidth). To scale beyond a single machine, state must be partitioned or replicated, and traffic must be distributed across an array of instances seamlessly.

Mental Model: The Multi-Tier Funnel

Do not conceptualize load balancing as a single box. At scale, it is a multi-tier funnel moving from global network routing down to application-aware distribution. Traffic is filtered, shaped, and routed progressively deeper into the infrastructure.

The Tiers:

  • Tier 0 (DNS & Global Routing): Resolves domains to IP addresses. BGP Anycast routes packets to the nearest geographic datacenter based on network topology.
  • Tier 1 (Layer 4 - Transport): Hardware or highly optimized software (eBPF/XDP, DPDK). Operates on IP and Port. Inspects no payload. Distributes packets to Tier 2 based on connection tuples.
  • Tier 2 (Layer 7 - Application): Terminates TLS, parses HTTP/gRPC headers. Capable of intelligent routing (e.g., sending `/api/video` to Video servers), rate limiting, and sophisticated retries.

L4 vs L7 Architecture & Tradeoffs

Choosing where to terminate network traffic fundamentally impacts CPU overhead, latency, and observability. Understanding the OSI model mapping is a non-negotiable requirement for system design.

Layer 4 Load Balancing (TCP/UDP)

Operates at the transport layer. Routing decisions are made solely on the 5-tuple: (Source IP, Source Port, Dest IP, Dest Port, Protocol).

Mechanics

The LB alters the destination IP of packets (NAT) or modifies MAC addresses (DSR) to forward traffic. It does not terminate the TCP connection; it passes packets through. The actual TCP handshake happens between the client and the backend server.

Tradeoffs

  • Pros: Blazing fast. Ultra-low latency. Minimal CPU usage (no TLS decryption). Handles millions of concurrent connections easily.
  • Cons: Blind to application context. Cannot route based on URL path or HTTP headers. Sticky sessions require IP hashing, which handles NAT'd clients poorly.

Layer 7 Load Balancing (HTTP/HTTPS/gRPC)

Operates at the application layer. The LB terminates the client's TCP connection, decrypts TLS, parses the payload, and creates a new TCP connection to the backend server.

Mechanics

Requires two separate connection pools: Client ↔ LB, and LB ↔ Backend. Because the LB parses the payload, it can read HTTP headers, cookies, and URLs. It can inject headers like X-Forwarded-For.

Tradeoffs

  • Pros: Deeply intelligent. Enables URL-based routing, header rewriting, WAF (Web Application Firewall) execution, and cookie-based sticky sessions.
  • Cons: Computationally expensive (parsing HTTP, cryptographic overhead of TLS). Can become a bottleneck. Higher latency due to proxying overhead.

Direct Server Return (DSR)

A highly optimized Layer 4 load balancing technique to solve the bandwidth asymmetry problem.

The Problem DSR Solves: In typical proxying, the response from the server must go back through the LB. In video streaming or file downloads, requests are tiny (bytes), but responses are massive (gigabytes). The LB becomes a massive network bottleneck on the outbound path.

How DSR works: The LB receives the request, leaves the Destination IP intact (which is the Virtual IP / VIP of the service), modifies the MAC address, and forwards the packet to a backend. The backend is configured to accept packets for the VIP, processes the request, and responds directly to the client's IP, bypassing the LB entirely.

Round Robin & Weighted Round Robin

Distributes requests sequentially across a list of servers.

Mechanics: Maintains an index, increments per request, modulo server count. Weighted assigns higher capacities to more powerful instances.

Production Reality: Dangerously naive at scale. It assumes all requests take equal time and all servers have equal capacity. If Server A is processing a heavy database export while Server B processes quick cache hits, Round Robin will blindly send identical traffic volumes to both, leading to CPU starvation on Server A.

Production Engineering Perspective

Architectures that look pristine on a whiteboard often fail catastrophically in production due to operational realities. Load balancers are uniquely positioned to either prevent or cause cascading failures.

Anti-Pattern: SNAT Port Exhaustion

When a Layer 7 proxy forwards traffic to backends, it uses Source NAT. It acts as the client. TCP limits ephemeral ports to ~65,535 per IP. If you route massive traffic to a few backends, the LB will run out of ports and instantly drop new requests.

Fix: Increase backend IP count, use connection pooling, or assign multiple IP addresses to the load balancer interfaces.

Anti-Pattern: Retry Storms

If a backend is slow, the LB might timeout and retry. If configured aggressively, the LB multiplies the traffic load on a struggling backend, pushing it from "slow" to "dead". This triggers cascading failure across the cluster.

Fix: Implement strict circuit breakers and retry budgets (e.g., max 10% of requests can be retries).

Operational: Connection Draining

During a deployment, you cannot simply terminate old backend processes, or active users will see 502 Bad Gateway errors.

Fix: The LB must support Connection Draining. The instance is removed from the active pool for *new* traffic, but existing established TCP connections are allowed to complete their requests (usually up to a 30-60s timeout).

Observability: High-Signal Metrics

Do not monitor average latency. Averages hide outliers. Monitor:

  • P99 / P99.9 Latency: The tail latency dictates user experience.
  • 5XX Error Rates by upstream.
  • Active vs Idle Connection counts.

Common Misconceptions

Nuances often overlooked by those without operational experience.

"Sticky Sessions (Session Affinity) are a good way to maintain state."

Reality: Sticky sessions create massive uneven load distribution (hotspots). If a highly active enterprise client gets "stuck" to Server A, Server A will melt down while Server B sits idle. It also breaks horizontally scaling, as taking a node down destroys the session state for all pinned users. State should be pushed out of the app tier into a distributed cache (e.g., Redis).

"Hardware Load Balancers (F5/A10) are obsolete."

Reality: While cloud-native software LBs (Envoy, HAProxy) dominate modern application architectures, hardware LBs using specialized ASICs are still extensively used at the edge of physical datacenters. They handle massive volumetric DDoS mitigation and line-rate BGP routing that general-purpose CPUs cannot efficiently process.

"Health checks guarantee traffic is only sent to healthy nodes."

Reality: Simplistic active health checks (pinging /healthz every 5 seconds) are often insufficient. A node might respond to the health check but fail to process complex database queries. Modern systems employ Passive Health Checking (Outlier Detection), where the LB evicts a node if it observes consecutive 5xx errors on actual user traffic, reacting in milliseconds rather than waiting for the next active polling interval.

Scenario

How do you load balance millions of persistent WebSocket connections?

(Click to flip)

Round Robin/Least Conn fails here due to connection longevity. Deploy an L7 proxy (e.g., HAProxy/Envoy) tuned for high file descriptor limits. Use Consistent Hashing (by user ID) to ensure reconnections hit the same stateful server. Monitor for "connection hoarding" during deployments.

Failure Mode

A backend node fails, is marked unhealthy, then restarts. It immediately crashes again. Why?

(Click to flip)

The Thundering Herd. When the node restarted, it had 0 active connections. The "Least Connections" algorithm funneled an immense spike of traffic to it before its caches were warm or DB connection pools initialized. Fix: Implement a "Slow Start" warmup period in the LB.

System Design

How do we ensure the Load Balancer itself isn't a Single Point of Failure?

(Click to flip)

Deploy LBs in Active-Passive (using Keepalived/VRRP for IP failover) or Active-Active clusters. For massive scale, use BGP Anycast to announce the same Virtual IP from multiple L4 load balancers (e.g., Maglev architecture), distributing traffic seamlessly across the LB tier itself.
