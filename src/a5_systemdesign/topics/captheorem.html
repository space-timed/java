System Architecture Core

The CAP Theorem

A foundational principle in distributed systems engineering dictating the boundaries of state synchronization across unreliable networks. It formalizes the tradeoffs between data recency and system uptime under partition scenarios.

Mental Model: You cannot guarantee that a geographically distributed system will always respond instantly and perfectly accurately when the physical network between its nodes fails. You must choose how the system degrades.

First Principles & Definitions

To analyze systems accurately, the terms must be defined strictly. Colloquial definitions of CAP terms often lead to flawed architectural decisions.

Consistency (C)

Strict Definition: Linearizability.

Every read receives the most recent write or an error. In a consistent system, once a write completes, all subsequent reads from any node must return that newly written value. The system must act as if there is only one copy of the data.

Availability (A)

Strict Definition: Non-error response guarantee.

Every non-failing node returns a valid response to every request in a finite amount of time, without guarantee that it contains the most recent write. It prioritizes returning some data over returning an error.

Partition Tolerance (P)

Strict Definition: Network resilience.

The system continues to operate despite an arbitrary number of messages being dropped or delayed by the network between nodes. A partition is a communication break.

Crucial Context: In distributed systems over wide-area networks (WAN), Partition Tolerance is not an option; it is a reality. Networks will fail. Packets will be dropped. Therefore, the architectural choice is never between C, A, and P. The choice is strictly between CP and AP when a partition occurs.

The Core Tradeoff: When the Network Breaks

Assume a simple distributed database with two nodes: Node A and Node B. Data is replicated synchronously. A network cable is severed between them (a Partition).

Behavior under Partition

A client attempts to read from Node B, but the latest write was sent to Node A. Because Node B cannot communicate with Node A to verify it has the latest data, Node B must return an error or timeout to the client.

  • Tradeoff chosen: It sacrifices Availability (returning an error) to ensure Consistency (preventing the client from reading stale data).
  • Use Cases: Financial transactions, inventory management, distributed locking systems.
  • Examples: HBase, MongoDB (default), ZooKeeper, etcd.

Behavior under Partition

A client attempts to read from Node B, but the latest write was sent to Node A. Node B cannot communicate with Node A. Node B returns the stale data it currently holds.

  • Tradeoff chosen: It sacrifices Consistency (client gets stale data) to ensure Availability (client gets a response instead of an error).
  • Use Cases: Social media feeds, product reviews, analytics platforms where eventual consistency is acceptable.
  • Examples: Cassandra, DynamoDB (eventual consistency mode), CouchDB, Riak.

Beyond CAP: The PACELC Theorem

A major limitation of the CAP theorem is that it only describes the system's behavior during a partition. But networks are largely healthy. What tradeoffs do we make during normal operation?

Daniel Abadi formalized the PACELC theorem (2010):

If Partition, choose Availability or Consistency.
Else, choose Latency or Consistency.

During normal operations (the Else), a distributed system must trade off between Latency and Consistency.

System Focus Explanation Real-world Examples
PC/EC During a partition, chooses Consistency. Else, chooses Consistency (sacrificing latency for synchronous replication). VoltDB, Google Spanner (mostly), etcd.
PA/EL During a partition, chooses Availability. Else, chooses Latency (asynchronous replication, eventual consistency). Cassandra, DynamoDB (default), Riak.
PA/EC During a partition, chooses Availability. Else, chooses Consistency (complex to implement, attempts synchronous replication when healthy). MongoDB (depending on configuration).

Production Engineering Perspective

How CAP/PACELC theory maps to operational realities and infrastructure decisions.

Observability & Monitoring

When operating an AP system (like Cassandra), monitoring consistency lag is critical. You must emit metrics on replication delay. If the p99 replication delay spikes beyond your acceptable business threshold, the system is technically "Available" but functionally degraded for users expecting near-real-time updates.

Handling Split-Brain

In CP systems, partitions require a mechanism to determine which side of the partition accepts writes. This introduces the requirement for Quorum consensus algorithms (Paxos, Raft). If a datacenter is cut off, and its nodes cannot form a majority (N/2 + 1), it must mathematically refuse writes to preserve consistency.

Scenario 1: Global E-Commerce Cart

You are designing a shopping cart for a global e-commerce site. Would you choose a CP or AP system for storing cart data? Defend your choice.

Click to reveal

AP System (e.g., DynamoDB/Cassandra).

Availability is paramount for revenue. If a user cannot add an item to their cart due to a network partition preventing consensus, the company loses money. It's better to accept an eventual consistency conflict (e.g., an item added twice, or a deleted item reappearing) and resolve it asynchronously during checkout, rather than blocking the user.

Scenario 2: Distributed Locking

You are building a microservice that generates strictly sequential, globally unique invoice numbers. You need a distributed lock. AP or CP?

Click to reveal

CP System (e.g., ZooKeeper/etcd).

Consistency is non-negotiable. If a partition occurs and the system favors availability, two separated components might both acquire the lock (split-brain) and generate duplicate invoice numbers, causing catastrophic data corruption. A temporary outage (unavailability) is vastly preferable to duplicate financial records.

Learning Roadmap

  • Foundation: Read Brewer's original conjecture (PODC 2000).
  • Formal Proof: Read Seth Gilbert and Nancy Lynch's paper, "Brewer's conjecture and the feasibility of consistent, available, partition-tolerant web services" (2002).
  • Evolution: Read Daniel Abadi's paper on PACELC to understand latency tradeoffs.
  • Mastery: "Designing Data-Intensive Applications" by Martin Kleppmann (specifically Chapters 5, 7, and 9). Focus on Linearizability vs. Serializability and Distributed Consensus.
